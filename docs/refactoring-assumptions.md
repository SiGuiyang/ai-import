# V4 重构假设说明

## 1. 文件类型的处理

**假设**: 上传的文件类型限定为 `.xlsx` / `.xls`。

**原因**: 当前 V2 的 `preprocessFile` 已支持这些格式。PDF/DOCX 的表格提取逻辑较复杂且非核心路径，V4 阶段不扩展。

---

## 2. 处理单元（Shard）大小

**假设**: 每个分片固定 1000 行，不可配置。

**推导**: 1000 行平衡了单批次耗时（~10s）和数据库批量操作的性能收益。2 个 Worker 并发可满足 10,000 行 ≤ 60s 的 SLA。

---

## 3. Worker 部署形态

**假设**: Worker 不部署在 Vercel 上，而是独立进程部署在 Railway/Render。

**原因**: Vercel Functions 有执行时间限制（10s/60s），无法满足长任务处理。独立 Worker 进程通过 `npm run worker` 启动，内部使用 BullMQ 消费 Redis 队列。

---

## 4. Outbox 模式的实现方式

**假设**: 上传 API 创建 outbox 记录后，由 outbox 分发器异步投递到 BullMQ。

**实现方案**: 
- 上传 API 直接写 `event_outbox` 表
- Worker 进程中运行 outbox 分发器定时轮询（1s 间隔）
- 发送成功后更新状态为 `sent`
- 失败 5 次后标记为 `failed`

**备选方案**: 上传 API 直接调用 BullMQ.add()（更简单但可靠性略低，如果 Redis 故障可能丢失事件）

---

## 5. 解析规则（Rule）的处理

**假设**: 如果上传时提供了 `ruleId`，Worker 会使用对应规则解析；否则使用原始解析（parseFile）。

**边界情况**: 如果指定的 ruleId 不存在，降级为原始解析。

---

## 6. SKU 校验降级策略

**假设**: SKU 校验超时阈值设为 3 秒。

**降级行为**:
1. `sku_master` 查询耗时 ≥ 3s → 降级
2. `sku_master` 表异常（连接超时等）→ 降级
3. 降级后仅做格式校验，`degraded` 标记为 `true`
4. 降级不可逆（单任务生命周期内）

---

## 7. 数据库 UPSERT 策略

**假设**: 不实现 UPSERT，使用简单的 INSERT。

**原因**: 每个分片处理不同的行范围，不会出现重复插入。如需真正 UPSERT，需在 `orders` 表上建 `(task_id, external_code)` 唯一索引。

---

## 8. 任务重试策略

**假设**: BullMQ 层配置 3 次重试，指数退避（1s, 2s, 4s）。

**行为**:
- Shard 级别重试（Job 失败 → 自动重试）
- 重试 3 次后标记为永久失败
- 任务级别的 `failedRows` 会累计

---

## 9. 监控数据存储与展示

**假设**: 监控数据直接查 PostgreSQL（不额外引入时序数据库）。

**局限**:
- 监控看板每 5s 自动刷新，查询性能依赖数据库
- 历史数据不会自动清理（需后续添加 TTL 策略）

---

## 10. 大文件处理

**假设**: 最大文件大小为 20MB。

**原因**: 1MB 的 Excel ≈ 50,000 行，20MB ≈ 1,000,000 行。当前场景以 10,000 行为典型值，20MB 足够。

---

## 11. 事务边界

**假设**: 以下操作不保证原子性：
- 创建任务（import_tasks）
- 创建分片（import_task_shards）
- 创建出箱事件（event_outbox）

**原因**: 简化实现。如果创建分片失败但任务已创建，任务状态为 `pending` 且无分片，不会产生副作用。

---

## 12. 上传文件内容存储

**假设**: 文件内容以 base64 存储在 `import_tasks.file_data`。

**替代方案**: 存储到 S3/Cloudflare R2，仅保存 URL。当前方案更简单但数据库存储成本高。
